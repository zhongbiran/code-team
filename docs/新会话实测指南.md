# 新会话实测指南

> 2026-11-23。目标：用一个**真实的小任务**跑通整条链路，验证每个角色的行为是否符合预期。

## 实测前必须先做的两件事

### 1. 插件要在新会话里生效

插件目录不是热加载的。当前状态：

- 插件已装在 `C:\Users\biran\.minimax\plugins\code-team`
- 控制台 MiniApp 已发布运行（`code-team-board`）

**开新会话前确认**：打开 `/plugins` → `Ctrl+R` 刷新 → Code Team 处于启用状态。
启用后**重开会话**，skill 才会出现在可用列表里。

### 2. Code Team 侧的 Codex 环境要同步过

Codex 是全新环境，只认 `~/.codex/AGENTS.md`、项目级 `AGENTS.md` 和 `~/.codex/skills/`。
第一次在新项目里用，先跑一次：

```bash
cd C:\Users\biran\.minimax\plugins\code-team
node scripts/codex-bootstrap.mjs <你的项目目录> sync
```

这一步把角色约定（Overmind/Coder 各做什么、只读、输出契约）写进 Codex 的全局 AGENTS.md，
并把项目的 skill 同步过去。**不做这一步，Overmind 开的会话看不到你的验收命令和已知坑。**

## 选什么任务来测

### 好的实测任务长这样

- **小**：3-6 个文件，一两个小时能做完
- **真**：你确实想做的事，不是玩具
- **有并行空间**：能拆成 2-3 个不重叠的包
- **有明确验收**：能跑一条命令判断成没成

### 不要用这些测

- 单文件改个错字（不会触发任何角色，白测）
- 纯调研任务（没有 Worker 派工，看不出拆包对不对）
- 大型重构（一次跑不完，看不出会话级问题）

### 推荐：拿你手上真实的下一个功能

比如「给设备列表加个 CSV 导出」这种：涉及前后端、能拆包、有明确的验收命令。

## 怎么开这一场

### 第一句怎么说

直接说：

```
用 Code Team 给设备列表加一个 CSV 导出功能。
验收：导出的 CSV 表头和设备列表一致，能被 Excel 打开。
```

**把验收标准写进第一句**。这不是多余的——Overmind 的 brief 里 `Done` 那一栏就是从这来的。
你自己不定清楚，Overmind 只能猜，猜错了整套流程都歪。

### 预期你会看到什么

```
你：需求
  ↓
主会话：原样转交 Overmind（不判断该不该开）
  ↓
Overmind（gpt-6.2-astra）：读代码 → 决策记录 → 拆包 → 每包 brief → 指明哪几包要 Coder
  ↓
主会话：原样转发
  ↓
Coder（gpt-6.2-sol）：只对 Overmind 指明的包给接口/取舍结论
  ↓
主会话：原样转发 brief 给 Worker ×N（并行）
  ↓
Worker：按 brief 做，只改自己那几个文件，自测
  ↓
主会话：派 Verifier 一次（干净 context，只拿 diff + 需求 + 测试结果）
  ↓
主会话：核对 → 汇报 → 记录纠正
```

## 观察什么（这才是实测的重点）

不要只看「做完了没」。要看这五件事：

| 观察点 | 合格的样子 | 不合格的样子 |
|---|---|---|
| **决策在哪** | Overmind 给了带理由和代价的方案 | 主会话自己拍板，Overmind 只是转发 |
| **brief 质量** | `Done` 是「一条命令 + 期望输出」 | `Done` 写「覆盖 A/B/C 三个场景」 |
| **拆包** | 文件归属不重叠 | 两个包改同一个文件 |
| **越界** | Worker 只改 brief 允许的文件 | 顺手改了 README 或加了依赖 |
| **验收** | Verifier 独立跑过一次 | 主会话自己验一遍就交付 |

## 中途怎么追加要求

直接说就行，**不要指望主会话自己消化**：

```
另外导出的文件名要带日期。
```

主会话会用 `--resume` 追加给 Overmind（复用同一线程，不重开、不浪费前缀缓存）。

## 测完之后

### 1. 看控制台

打开 Code Team 控制台（`/plugins` 里的 Mini App，或直接说「打开 Code Team 控制台」），
重点看**问题诊断**页——它会直接告诉你这次运行哪里不对：

- 规划返工：Overmind 开了几次
- 只规划没落地：Coder 开了但没有 Worker
- 验收缺失：有 Worker 但没 Verifier
- 前缀未复用：缓存命中率低（说明没走 --resume）

### 2. 记纠正

这次实测中，你肯定会纠正它至少一次。把纠正记下来：

```bash
cd C:\Users\biran\.minimax\plugins\code-team
node scripts/lessons.mjs record "<你纠正的原话>"
```

同一条纠正记两次，它就该升级成检查：

```bash
node scripts/lessons.mjs list                    # 看哪些到了 2 次
node scripts/lessons.mjs promote <ID> "<检查脚本名>" "<描述>"
node scripts/lessons.mjs check                   # 跑所有检查
```

**这是「持续提升」真正发生的地方**——不是插件自己变聪明，
是你每次的纠正都被固化成会自己失败的检查，下次不用你再说。

### 3. 导出周报

控制台「配置」页有「导出周报 Markdown」，或者直接 `GET /api/report`。
周报里的「优化支撑点」是从数据算出来的，会指出：
哪个模型最耗时、缓存命中率如何、消耗集中在哪个项目。

## 花钱前先看一眼额度

Codex 和 MCode 是**两套独立的额度**：

- Codex 侧（Overmind/Coder）：`node scripts/codex-team.mjs budget`
- MCode 侧（子代理）：opencode-go 的 rolling / weekly / monthly 三档

实测前跑一下 `budget`，心里有个数。Codex 每次规划调用约 20K-90K input token，
**一次 Overmind 规划按 50K 估**。

## 出问题时的排查顺序

1. **控制台的问题诊断页** —— 多数情况直接写清楚了原因
2. `node scripts/lessons.mjs check` —— 两条自动检查过了吗
3. `codex debug prompt-input ...` —— 确认 Codex 真的读到了你的项目规范
4. 插件的 `references/` —— 每个环节的细节都在那

## 附：skill 调用机制的验证（2026-11-24 新增）

本轮给 Code Team 加了「角色 → skill 名单」机制：名单在 `config/team.json` 每个角色的
`skills` 字段里；`scripts/codex-team.mjs` 每次调用自动点名该角色的 skill，
派工时用 `scripts/skills-for.mjs <role>` 把提示原样贴进 Task prompt。

### 第 1 步：零成本看注入内容

```bash
node scripts/codex-team.mjs plan --role overmind --prompt-file <需求.md> --print-prompt
```

`--print-prompt` 只打印拼好的 prompt，**不发请求、不记事件、不烧额度**。
尾部应看到「## 本次可用 skill」和该角色的名单。

### 第 2 步：确认配置里的 skill 真的存在

```bash
node checks/skills-exist.mjs
```

skill 名写错是**隐形失败**——流程照跑不报错，只是方法论从没被加载过。
这个检查已经红测过（故意改坏一个名字 → exit 1）。

### 第 3 步：新会话里确认 MCode 侧看得见新插件

MCode 的插件列表是**会话启动时的快照**。本轮新装的 `context-engineering`
（19 个 skill，MIT）在装它的那个会话里是看不见的（实测子代理报
`context_engineering_count=0`）。

新开一个会话，让子代理报一下：

> 列出你当前可用的 skill 中带 `context-engineering:` 前缀的条目

期望 19 条；`superpowers:` 14 条也应同时可见。

## 一句话总结

实测的目的不是「让它做完」，是**看它每个角色的行为对不对**。
做完了但决策是主会话做的、brief 没写清验收、Worker 越界了——这些都要在控制台上看出来。
