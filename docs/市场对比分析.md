# 与 MiniMax 插件库对比：Code Team 的定位、差距与提升点

> 2026-11-23 核实。依据：官方市场目录（135 个插件）、官方文档（Agent Team / Mini App / 插件市场）、
> 本机已装插件实测、以及 dsh-token-stats 参考项目。

## 一、市场里有没有现成的？

搜过市场（catalog_size 135，全量扫过）并读了官方文档，结论分三类：

| 类别 | 代表 | 与 Code Team 的关系 |
|---|---|---|
| **官方 Agent Team**（MCode 内建能力，不是插件） | Agent Team | 概念相同——拆解、协作、校验。但它由 MCode 内部编排，**角色和模型不可配**，也不产出用量统计 |
| **MiniMax Bot**（已装且启用） | MiniMax Bot | 最接近的对照：长期在线的 Bot 团队，**有用量统计** |
| **垂直领域插件** | 金融/企查查/法信/Office/WPS/企业微信 | 与 Code Team 无重叠 |
| **Mini App 类** | 股市看板、CadQuery Viewer、桌宠、Token 统计看板 | 形态相同（Mini App），内容不同 |

**没有任何插件同时满足"可配后端 + 多维归因统计 + 可导出周报"。**所以做 Code Team 是补空白，不是重复造轮子。

## 二、Code Team 现在的真实位置

```
主会话（侧边转交）→ Overmind（决策）→ Coder（代码方向）→ Worker/Explore/Verifier（执行）
                                    ↓
                          事件流 events.jsonl（后端无关）
                                    ↓
                          Code Team 控制台（MiniApp）
```

三层分工：

- **Code Team 插件**（`D:\.minimax\plugins\code-team`）：流程与决策层，定义角色、契约、埋点
- **Code Team 控制台**（`code-team-board` 仓库）：可视化与统计层
- **官方 mcode 插件**：方法论层（agent-brief / taste-to-checks 等判据，已装，不重复造）

## 三、对比 MiniMax Bot：它做了什么，我们差在哪

实测了本机 MiniMax Bot 的 liveboard 数据（`v2/plugin-data/liveboards/minimax-bot/usage.jsonl`），
它的每条记录长这样：

    {"ts":...,"botId":...,"botName":"Chief","chatId":...,"kind":"private|delegation",
     "status":"done|aborted","durationMs":...,"chars":...,"tools":...}

### 它比我们强的地方

1. **有余额与预警**。它能显示 DeepSeek 账户余额，低于阈值变红预警。
   我们的控制台目前**没有余额概念**——只有已用 token，看不到还剩多少。
2. **会话级角标**。对话标题栏常驻"本会话已用"胶囊，10 秒轮询。
   我们的统计只在独立页面里看，**看不到"当前这次会话"花了多少**。
3. **活动热力图**。12 个月日历网格，GitHub 风格。
   我们目前只有"按日消耗"表格，**没有时间维度的视觉密度**。
4. **下钻到单个会话/任务**。点日期看当天明细。
   我们的事件明细有原始事件，但没有**从汇总点进去**的路径。

### 我们比它强的地方

1. **归因维度更深**。它按 botName/chatId 统计；我们按 **项目 / 任务 / Skill / 插件 / 模型 / 后端** 六个维度归因。
   这直接对应"消耗集中在哪些项目、哪些任务、哪些 skill"这个问题。
2. **配置可视化**。它没有配置面板；我们能改 Overmind/Coder 的**后端与模型**，并写回 team.json。
3. **后端无关**。它绑死 DeepSeek；我们的事件流 `backend` 字段可换——换 Codex、换 Grok、换 MCode 自身，统计不用改。
4. **决策权分离**。它由主 Bot 编排；我们把决策权交给 Overmind，**主会话只是侧边会话**。

## 四、对比官方 Agent Team：差距在哪

官方 Agent Team 文档只说"根据任务复杂度引入多个专家 Agent 协作"，**没有暴露配置点**：
角色固定、模型绑定在插件里、拆分策略不可见、也没有用量归因。

Code Team 补的是它没给的三件事：

| 维度 | 官方 Agent Team | Code Team |
|---|---|---|
| 决策者 | MCode 内部 | 显式的 Overmind，**后端可换** |
| 决策模型 | 不可见 | `config/team.json` 可配 |
| 拆分依据 | 不可见 | Overmind 产出决策记录 + 拆包 + brief |
| 用量归因 | 无 | 六维度事件流 |
| 独立验收 | 内建但不可见 | 显式 Verifier，独立 context |

## 五、该补的提升点（按价值排序）

### P0｜余额与额度预警（缺口最大）

参考 dsh-token-stats 的余额预警：低于阈值变红、点击强刷。
Code Team 现在看不出"还剩多少额度"——只能看已用。
接 opencode-go 的三档（rolling / weekly / monthly）就能补上，本机看板已有现成实现。

### P1｜当前会话角标

MiniMax Bot 有"本会话 X"胶囊。我们的事件流有 `threadId`，
但**主会话的派工没有会话维度**——Task 工具调用在主会话里发生，事件里记的是 task 名。
补一个 sessionId 字段就能支持。

### P1｜活动热力图

我们只有按日表格。参考项目用 12 个月日历网格 + 每日/每周/累计三视图。
这是"每周复盘"最直观的视觉入口——一眼看出哪周异常。

### P2｜汇总下钻

现在从 KPI 数字点不到明细。补一条"点维度 → 展开该维度的所有事件"的路径。

### P2｜周报自动生成

目前要手动点导出。按你的诉求（"每周做优化分析"），
应做成**定时任务自动跑**——用 MCode 的 cron 每周一跑一次，
把周报落到固定位置。这是官方 `schedules.md` 的能力。

### P3｜对比基准（eval）

官方 `coding-agent-eval` 强调：改 Harness 要有小型端到端 eval，
"一次只改一处，看哪些任务翻转了"。
Code Team 改模型/改档位/改流程时，目前没有基线可比。
控制台的历史事件流正好是天然的 eval 数据源——但要能对比"改之前 vs 改之后"。

## 六、不该做的

- **别做成通用的"Token 统计"工具**。参考项目是 DSH 专属（解析它的 zstd 日志）。
  我们的价值在于**跨后端 + 项目/任务/skill 归因**，不是又一个 token 计数器。
- **别重复实现官方 mcode 插件的 skill**。agent-brief / taste-to-checks 等已装，
  引用它们，不要复制一份到 Code Team 里（会漂移）。
- **别让 MiniApp 自己跑 Codex**。统计只读事件流，调用仍走插件脚本——
  否则会出现两套调用路径，统计口径立刻分裂。

## 七、本次实测覆盖与未覆盖

**已验证**：

- 配置写回 team.json（浏览器操作 → 文件真变，`note` 等未白名单字段没丢）
- 事件流写入（Codex 调用带 project/task/skill/plugin 归因）
- 看板渲染全部维度（项目/任务/Skill/模型/按日）
- 报告聚合逻辑（按项目/任务/Skill 拆解正确）

**未验证**：

- 周报端点 `/api/report` 的 HTTP 响应（聚合逻辑单测通过，但没在浏览器里点过下载）
- `mcode-agent` 后端（配置已写，**没实跑过**）
- 派工埋点的真实数据（skill 里写了埋点规则，**还没按它派过工**）
- 余额预警（P0，尚未实现）
