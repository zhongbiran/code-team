## 一、核心判断：什么时候该开子代理

官方《subagent 不是越多越好》（mcode-notes-01-subagent）给的判据是机械可执行的：

| 判据 | 原文依据 | 落到我们怎么做 |
|---|---|---|
| 这段工具输出，后面还要再看，还是只要一个结论？ | 只要结论，才适合交给 subagent | 只要结论 → 派 Explore/Worker；要反复引用原文 → 主会话自己读 |
| 单循环出现了**可测出的**效果下降 | 要有 eval 数据，光凭感觉不算 | 没有 eval 就别按感觉拆 |
| 有几件事要并行做，每件都要干净 context，做完可扔 | 互不相干的调研路线 | 满足则并行开 Worker |
| 主 agent 选不对工具，或 system prompt 指令互相冲突 | — | 工具打架时再拆 |

**切法**：按 context 切，不按问题类型切。好的切法是"子任务几乎不依赖系统其他部分，做完交回一个紧凑结果"。按问题类型拆会退化成"传话游戏"，每交接一次丢一点细节。

原文点名的失败模式：交接有损、subagent 越长越多、system prompt 变成缝合怪、eval 各管一段、延迟叠加（单循环比多 agent 快约 2 倍）、架构长成组织架构图。

**官方立场**：日常开发"尽量一个任务一个会话，不额外拆 subagent"，反复用的流程写成 Skill。

## 二、额度与上下文纪律

### 2.1 前缀缓存：位置比数量重要（mcode-notes-05-prefix-cache）

> **缓存按前缀匹配。前面有一个字节变了，后面就全部作废。**

三种放置方式代价天差地别：

1. **最前面、每轮都变** → 代价最大。后面所有内容全部 miss。原文举例：精确到秒的时间塞进系统提示词，每轮让整段前缀失效。
2. **写进历史、写完不再改** → 影响有限。第 5 轮写进去的内容，第 6 轮已是前缀的一部分。
3. **只挂在请求末尾、不进历史** → 永不缓存，但每发一次就是一份全价输入。

原文的结论很反直觉：**一个几十 token 的字段，放错了位置，可能比几千 token 的工具定义还贵。**

推论（原文给出的"位置三类"）：
- 不变的放前面，会变的往后放
- 写进历史的东西不回头改
- 精度够用就行（原文把日期精度从秒改成分钟）
- 给每段注入内容标两个属性：「多久变一次」和「放在哪」

MCode 的实际做法：系统提示词的 `# Environment` 只放会话内不变的东西；当前时间写进每轮用户消息开头的 `<agent-context>`。

**对我们的意义**：Code Team 插件的 skill 正文、需求文件里的固定段落要放在稳定位置；每次都变的（比如当前时间戳、随机 ID）不要塞进长期前缀。

### 2.2 工具数量阈值（mcode-notes-02-tool-search-ptc）

| 数字 | 含义 | 来源 |
|---|---|---|
| **30-50 个工具** | 超过后模型选工具就开始变差 | mcode-notes-01-subagent / -02 |
| 58 个工具 / 约 55K token | 只接 5 个 server 的定义开销（Anthropic 内部见过优化前占到 134K） | mcode-notes-02 |
| 约 117 万 token | Cloudflare 2500+ API endpoint 全做成原生 MCP 工具的定义体积 | mcode-notes-02 |
| **每组少于 10 个函数** | OpenAI tool search 文档建议的 namespace 分组粒度 | mcode-notes-02 |
| **85%** | tool search 能降的工具定义开局开销（Anthropic 数据） | mcode-notes-02 |
| 49% → 74% / 79.5% → 88.1% | 开 tool search 后 Opus 4 / 4.5 的准确率提升 | mcode-notes-02 |
| 落后 19 个点 | 某 tool search 方案在 525 个真实 MCP 工具上的召回差距 | mcode-notes-02 |

原文的三步走：**先做减法 → tool search（延迟加载）→ PTC（写程序调工具）**。MCode 默认开 tool search，MCP 工具按规模自动切换。

PTC 的关键结论：**PTC 不会让模型更聪明，它只是让同样的活少发几次请求**，省下来的开销几乎全部来自请求次数变少。原文还踩过一个坑：把派 subagent 也挪进程序后，它被用得明显少了——所以和用户交互、改会话状态、派 subagent 的工具必须留在顶层。

按瓶颈分层叠加（原文引用 Anthropic 的建议）：
- 定义太大 → tool search
- 中间结果太多 → PTC
- 参数总传错 → 给工具加用例
- 只调一次的简单操作、模型必须亲眼看到中间结果才能决策的场景 → 别硬塞进程序

### 2.3 PTC 在本机的实际形态

本机 MCode 已开启 PTC（`run_code` 工具）。本文档中的所有批量读取与并行查询都是一次 `run_code` 调用完成的——这正是 PTC 省 token 的体现。

### 2.4 compaction 与 memory（mcode-notes-03-compaction-memory）

context window 是工作台，不是仓库。原文的分工：

- **compaction** 管长历史：会话越来越长时压缩，保住能继续干的状态
- **memory** 管跨会话：把要紧的沉淀到对话之外

关键点：**重要状态别只活在 context window 里**。长任务开始就建一份设计或进度文档，把计划、关键决策、排除过的方案、review 结论随时写进去。新会话开始或换人接手，直接 @ 这份文档就能接着干。

配套的好处：少了很多"为了保住 context 才拆 subagent"的冲动——状态已经在文档里了，会话可以放心清空重来。

### 2.5 后台任务与长命令（mcode-notes-04-bash-background）

原文讲的是"停顿税"：让 agent 干等一条 bash 命令，等于让前缀缓存**过期**（护的是缓存寿命，05 护的是缓存命中）。

原则：能后台跑就后台跑，别让模型在前台干等；后台任务要有通知、防轮询、回收机制，压缩后还要能提醒。

**对我们**：Code Team 的 Codex 调用有 12-36 秒延迟，绝不能前台干等；应该后台跑 + 完成后通知。本插件脚本已支持这一点。

## 三、审查者独立性（mcode-notes-01-subagent / coding-agent-workflow-and-skills）

> 写代码的 agent 和审查代码的 agent，**不共用一份 context**。

原文的理由很朴素：写代码的 agent 一路上做了很多决定，也一次次说服了自己。审查者要是继承了这段对话，就会顺着同样的思路去看代码，作者漏掉的地方它多半也会漏掉。

**只给审查者三样东西**：diff、需求说明、测试结果。
**不给**：作者的对话过程和中间推理。

审查者要回答的是"这份改动有没有满足需求"，不是"作者的思路讲不讲得通"。

原文举的例子极典型：作者 agent 在对话早期给自己定了个前提（"这个函数的调用方都已经做过空值校验"），后面的代码都建立在这个前提上。让它自己 review，它会顺着同一个前提往下看，自然看不出问题。独立的审查者手里只有 diff 和需求，反而会直接问：这里传进来的值为空怎么办？

**结论以结构化意见交回主循环**（逐条问题、位置、理由）。主循环**不照单全收**，而是对照真实代码和测试逐条核实，确认成立了再改。

对应到工作流文章：`deliver` 的每个里程碑都要"让一个全新的子 Agent 对照 spec 检查"；`core-spec` 写的两份文件（spec.md / verify.md）由"另一个模型家族在全新的只读会话里检查，不带上作者的推理过程"，**找不到这个审阅者就不冻结**。

## 四、需求定义与验收（coding-agent-workflow-and-skills / coding-agent-eval）

### 4.1 人参与的位置

原文的分工非常明确：**人只需要参与三个位置**——回答问题、确认 spec.md 和 verify.md、最后看决定清单并合入。

七条原则里最相关的几条：
1. **你定目标和检查方式，然后走开**——目标和验收方式由人定，执行交给 agent
2. **一个 Agent 从头负责到尾**——交接会丢上下文（作者实测：一次交接让计划少了近 600 行）
3. **Agent 能运行、操作和观察真实产品**——只编译不算，要真跑
4. **计划和进度放在仓库文件里**——状态只在聊天里，下个会话只能猜
5. **做得对不对，由别人来判断**
6. **Agent 卡住时，修仓库，不只改提示词**——提示词里的规则是下一个 agent 可能跳过的要求；写进代码的规则每次都会执行
7. **复杂度值得加时再加，一次加一点**——作者试跑后规则从 3 个涨到 11 个，指令篇幅增加约 70%，后来又删回 1 个

### 4.2 eval 的三个要点（coding-agent-eval）

- 一道题得带上环境和验收方法；参考修复、隐藏测试、评分程序留在评测侧（否则答案可能和题目一起送进去）
- 题入库前检查：未修复版本确实失败、参考修复能稳定通过、在干净环境重跑（排除本机残留）
- **开发集 / 验证集 / 最终留出集**要切分。一直盯着同一批题改 Harness，分数上涨未必代表新任务做得更好；留出集看得多了就该承认它已经是开发集的一部分

成本记账的纪律（对我们做额度账本直接适用）：用量可能缺失，**未知部分保留未知，能确认的费用记作下界**。把缺失填成零会低估成本；把可能重叠的缓存、推理、总 token 字段直接相加，则可能多算。

### 4.3 HAI：为什么人在哪一环（hai-principles）

原文的核心论点：委派 What（结果声明）之后，What 与 How 之间的鸿沟在于 **Why**。Agent 可以把权衡讲得头头是透，但它不承担现实后果，无法自己生长出 Why，**也就不该由它来拍板**。人唯一可靠遵循的准则，是人类将 Why 转化并固化下来的**产出契约**。

另一条对我们直接相关：**理想交互应当折叠可逆过程**，只在关键节点上呈现模型的假设。过度暴露中间细节会诱发审批疲劳（CHI 2021，3800 人预注册实验：面对内部清晰透明的模型，受试者发现并纠正重大错误的能力反而低于面对黑盒模型的受试者）。

## 五、工具与平台定位

### 5.1 Skill vs subagent vs Mini App（agent-as-os / minimax-code-mini-app / minimax-code-harness）

- **Skill**：放进 Skill 的是"团队反复用到的流程和经验"，平时只露一句描述，真用到时加载全文。主 agent 自己就能读到，不用多一层交接。
- **Agent 插件**让你改造 Agent；**Mini App** 让你在 Agent 之上做应用（有前端、有后端、长期运行、能在页面里处理工具审批）。
- **Harness 层**（minimax-code-harness）：能力按版本租用——每轮拿一份带 revision 的能力视图，模型读过某一版工具说明后，插件更新不会把本轮能力悄悄换成另一版。
- 上下文预算公式（原文）：`L = max(1, min(floor(0.95 × C), C − R, C − O_eff − S))`，默认 `R = 16,384`、`S = 2,048`；自动压缩阈值 `T = min(L, max(1, C − min(2×R, floor(C/4))))`。131,072 窗口 + 16,384 输出时，`L = 112,640`、`T = 98,304`。

### 5.2 什么是该做成 Skill 而不是 subagent

原文（mcode-notes-01-subagent）：代码规范、发布流程、内部库的用法和坑、验证和测试步骤——这些放进 Skill，和让一个专门的 subagent 去"负责规范""负责发布"相比，主 agent 自己就能在需要时读到。

**判断标准**：如果这条知识是"要在需要时查阅的"，做成 Skill；如果它是"一段独立的、上下文干净、做完可扔的活"，做成 subagent。

## 六、落地到 Code Team 插件

| 官方原则 | 插件里的具体做法 |
|---|---|
| 按 context 切，不按问题类型切 | Worker 按**文件归属**拆包，不按"前端/后端"这类角色切 |
| 审查者独立 context | Verifier 只拿 diff + 需求 + 测试结果，不给作者的对话 |
| 一次只合一个，改一处留证据 | 预算账本按调用记录 usage，模型可随时换，只改配置 |
| 计划和进度放在仓库文件里 | 计划落盘 `docs/plans/<date>-<slug>.md` |
| 重要状态别只活在对话里 | 账本 `config/usage-ledger.json` 落盘 |
| 别让模型干等（停顿税） | Codex 调用走后台，完成后通知 |
| 工具按需加载 | 三个子代理各自只拿自己需要的东西 |
| 上下文是预算 | 需求文件只放必要上下文，不塞无关大段 |

## 七、原文没覆盖的部分

以下问题官方博客**没有回答**，本方案里的对应做法属于工程决策而非官方结论：

1. **Codex CLI 与 MCode 子代理混编时的额度换算**——官方没有跨工具的额度换算表。本文给的 15%/10%/50%/25% 配比是按限流经验拍的，需按实际账本校准。
2. **具体项目的验收命令该写在哪**——官方讲的是"计划和进度放在仓库文件里"这个原则，没给统一模板。
3. **多模型并存时的模型选择策略**——原文讲的是"一个主 agent 配 Skill"，没有多模型编排的官方推荐。
4. **5 小时滚动窗口的具体数值**——官方博客完全没提订阅额度的限流细节。
