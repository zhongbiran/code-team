# 复盘 · 2026-11-27 RC.DustFall（防灭火第三方传感器联动 + WebAdmin 三处）

## 背景

一轮 Code Team 任务：现场反馈"第三方温度传感器 9.8 > 超限 5（恢复 2）却没发灭火开"。
Overmind 决策 1 次，拆 3 包并行，验收 1 次；随后用户追加了前端 5 类扩展、WebAdmin 三处修复、
以及三条流程纠正（本轮共 9 个包 + 1 个被掐掉的包）。

## 一、派工上下文窗口被顶到 1M（用户两次指出）

**现象**：worker/verifier 子会话 `contextWindowTokens = 1000000`；而内置
`agents/.builtin/{worker,verifier}/agent.md` 明明声明 `x-mavis.contextWindow: 512000`，
宿主 `config.yaml` 里 `defaultModelContextWindow` 也是 512000。

**根因（探针实测，不是猜）**：

| 探针 | 派工参数 | 子会话窗口 |
|---|---|---|
| A | 不传 model | 512000 |
| B | 传 `model: minimax/MiniMax-M3.1-Flash` | 1000000 |
| C | 传 model（宿主 config 去掉 1M 档之后，宿主未重启） | 1000000 |

显式传 model → 运行时**忽略 agent 自己声明的 contextWindow**，改用宿主模型目录里
`contextWindowOptions` 的最大值（M3.1-Flash 给到 1000000，标 `higher_usage`）。
窗口越大，每次模型调用重发的累积上下文越多，cacheRead 主导的账单线性放大
（本轮实测 cacheRead 占各子会话总 token 的 90%+）。

**规避（三层）**：
1. `scripts/dispatch-params.mjs`：**与 agent 自身声明相同的 model 不再下传**。
   agent 默认已经生效，显式下传同一个值只有代价没有收益；换模型（与 agent 默认不同）照常下传，
   控制台改模型依然真的生效。
2. 宿主 `config.yaml`：去掉模型目录里的 1000000 档（**要重启宿主才生效**）。
3. 新增 `checks/subagent-context-window.mjs`（台账 L-003，已升级为必跑检查）：
   盯**实际派工输出**——下传的 model 若与 agent 默认相同 → 红；下传的 model 在宿主目录里
   最大上下文 > 512000 → 红。红绿都验过（夹具喂旧行为 → 报 `model-overrides-agent-default`）。

## 二、探索包空烧

**现象**：`pkg-field` 的目标是"现场导出的日志目录"，本机根本没有 → 一个物理上不可达的包，
烧掉数百万 token，最后只产出"缺证"。

**根因**：派工前没做**证据可达性**检查。

**规避**：派工前三问 ——
① 这个包要的证据在本机/本仓库可达吗？不可达就别派，改成"产出现场取证清单"。
② 这个包的产出需要改代码吗？不需要就别占一个执行角色。
③ 能不能并进已有包？能就并，别单独开包。

## 三、brief 缺可证伪假设与止损条件

**现象**：心跳包 140 次工具调用、5.27M token、**零落盘**，只能掐掉重派。

**根因**：brief 写成"查清语义再改"，没给判定口径，也没给止损点 → 子代理在原地无限搜索。

**规避**：brief 必须写成「假设 → 可证伪的检查 → 结论」，并写死止损条件：
「查不到就报断点（文件:行 + 原因），不得继续扩散」。时间盒到点先看 `git status` 的落盘深度，
再决定续派还是改口径。

## 四、验证重复（用户指出：改代码 1 分钟，花了 25 分钟验证）

**现象**：worker 跑红绿 + 全量 + verify.ps1，verifier 又独立复现红绿 + 全量 + 静态检查。

**规避（验收分层）**：
- 执行者：只跑「编译闸 + 专项测试」。
- 验收者：只跑「一次专项测试」+ 读 diff，不重复全量。
- 全量 / `Scripts\verify.ps1`：编排者最后跑一次。

## 五、口径/枚举类改动必须一次覆盖六处

**现象**：kind 扩到 5 类后，存量行回读与保存口径不一致（前端原样回传旧 kind → 保存被拒），
又派了一个包补"类别按台账码统一解析"。

**规避**：口径/枚举类改动一个包必须一次覆盖六处 ——
枚举定义 → 映射表 → 读（回读/查询）→ 写与校验 → 存量兼容 → 前端契约。缺一处就现场配置改不动。

## 六、整批验收会被闸门拒

**现象**：`pkg-field`/`pkg-web` 是闸门外派工（没带 brief-ref）→ 闸门账本里没有它们的
"已终结"记录 → 带 `code-team-verification-key` 的整批验收直接被拒（包未全部完成）。

**规避**：同一批要么全走闸门（brief-ref + plan/package 标记），要么整批都不带 verification-key；
不允许混。

## 七、brief 注入会整体替换 prompt

**现象**：宿主按 sha256 注入 brief 正文时，主会话补的路径/约束被整体顶掉。

**规避**：需要路径或约束时，要么写进**需求文件**让 Overmind 落进 brief，要么走非闸门派工并
原样贴 brief 原文；不要指望"注入 + 我的补充"并存。

## 八、Overmind 写的验收命令可能在本仓库走不通

**现象**：brief 写 `dotnet test --filter ...`，而本仓库 .NET 10 SDK 下 `dotnet test` 走不通
（硬规则 11：构建到 %TEMP% + 直接跑测试 exe），worker 只能自己纠正。

**规避**：需求文件里必须附「仓库硬约束」清单（验收命令口径、临时产物落点、隔离红线），
让 Overmind 直接写对的命令。

## 九、注释 AI 味

**现象**：子代理写的注释复述代码、带"现场口径 / 11-27 问题"式叙事。

**规避**：brief 里写死注释纪律 —— 不写解释性注释，只写"代码本身表达不了的为什么"；
交付里附一句注释自查。编排者收尾时自己再扫一遍。

## 十、编排者越权边界

配置类改动（team.json / 宿主 config）属于编排职责，但要**在汇报里声明改了什么、为什么**；
测试断言更新属于集成职责（执行者改测试、编排者改过期断言），同样要声明。
涉及额度/成本策略的配置变更，先说清代价再动。
